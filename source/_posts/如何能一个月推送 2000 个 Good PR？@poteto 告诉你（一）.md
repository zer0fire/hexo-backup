# @poteto 的准则

## 一、Trust：如何让我们更加信任 Agent？

在 AI Coding 的过程中，我们经常会遇到一个问题：

Agent 告诉你已经完成了某项功能，代码看起来也没有明显问题，但你真的能确定它是正确的吗？

它是否真正运行了应用？是否复现了问题？是否验证了修改后的行为？是否存在没有覆盖到的边界情况？

### 1.1 建立 Verification Skill

首先，我们需要为项目建立一套专门的 Verification Skill（验证技能）。

它的目标不是简单地告诉 Agent 如何运行测试，而是让 Agent 能够像一个真正的开发者一样，启动应用、操作功能、复现问题、收集证据，并验证修改是否符合预期。

这里有两个关键组成部分：

**CLI：提供可操作、可复现的工具。**

CLI 是 Agent 与应用交互的基础设施。我们可以根据项目的特点，为 Agent 提供一系列工具，例如：

- Chrome DevTools Protocol（CDP）：控制浏览器、模拟用户操作、检查页面状态。
- Heap Snapshot：分析内存使用情况，排查内存泄漏。
- Performance Trace：收集性能数据，分析应用运行过程中的性能问题。
- 项目自定义 CLI：启动应用、执行测试、检查服务状态、获取运行日志等。

这些工具让 Agent 不再只是通过阅读代码推测程序行为，而是能够真正运行应用、观察应用，并收集可以复核的证据。

例如，当 Agent 修复一个页面性能问题时，我们不应该只让它告诉我们「已经优化完成」，而应该要求它提供优化前后的 Performance Trace、相关指标以及实际运行结果。

**Feature Map：让 Agent 知道如何使用应用。**

这是我认为整个验证体系中非常值得借鉴的一个设计。

对于复杂的代码库，可能连开发者自己都不清楚某些功能具体如何触发。

例如：用户相关功能需要登录后才能访问、某些活动相关的弹窗需要先进入特定页面，比如点击某个按钮、某个状态需要输入特定内容才能触发、某个异常只会在特定操作顺序下出现。

如果 Agent 不知道这些信息，即使拥有 CDP，也未必知道应该如何验证功能。

因此，我们需要建立一份 Feature Map（功能地图），记录应用中重要功能的入口、触发方式、操作步骤以及需要观察的结果。

它可以帮助 Agent：

1. 快速定位需要验证的功能。
2. 明确应该通过什么操作触发目标功能。
3. 根据具体任务按需加载相关功能说明，而不是每次都扫描整个应用。

这里的关键是：Feature Map 不应该成为一份庞大的应用说明书，而应该是一份能够按需检索的功能索引。

**CLI 解决怎么操作，Feature Map 解决操作什么以及如何触发。**

两者结合，才能让 Agent 真正具备验证应用的能力。

### 1.2 建立分层的信任体系
### 1.2 建立分层的信任体系

除了 Verification Skill，@poteto 还提出了一套值得借鉴的思路：我们应该从不同层次建立对 Agent 代码输出的信任。

可以将它理解为一个倒金字塔：越靠近代码本身和自动化工具，约束越明确、执行结果越确定；越依赖自然语言和人为判断，执行结果就越容易受到上下文和主观因素的影响。

**第一层：Codebase Improvements（代码库改进）**

这是最重要、也最值得投入精力的部分。

AI 倾向于继承代码库中已有的实现模式。它通常会参考现有代码的结构、风格和设计，然后在此基础上进行扩展。

因此，Codebase 不仅是 Agent 工作的对象，也是 Agent 的一部分 Memory 和 Context。

如果代码库中已经存在清晰、合理的实现模式，Agent 就更容易沿用这些模式；反过来，如果代码库充斥着技术债和 Anti-pattern，Agent 也可能不断复制这些问题。

我们可以通过改善代码库来降低 Agent 犯错的概率，例如：

- 明确模块职责，减少不必要的耦合。
- 使用更严格的类型约束，减少模糊的接口和数据结构。
- 建立清晰的数据模型和不变量（Invariants）。
- 统一常见问题的实现方式，避免同一个问题在不同模块中出现多种实现。
- 清理过时的 API 和不合理的历史实现。

与其反复告诉 Agent 不要犯某种错误，不如直接从代码结构上减少犯错的可能性，让正确的实现方式成为最自然的选择。

**第二层：Static Analysis（静态分析与自动化检查）**

这一层主要依靠工具提供确定性的约束。

例如：

- Linter：检查代码风格、潜在问题和不规范的实现。
- Compiler：检查类型错误和编译问题。
- Tests：验证功能行为和业务逻辑。
- CI：在代码提交或合并前自动执行各项检查。

这些工具有一个很大的优势：它们不依赖 Agent 是否正确理解了某项规则。

即使 Agent 忘记了某项要求，或者生成了不符合规范的代码，工具依然可以通过预先定义的规则发现问题，并提供明确的反馈。

相比反复消耗 Token 让 Agent 理解和遵循规则，静态分析和自动化检查能够以更低的成本提供更稳定的保障。

**第三层：Rules & Bug Bots（规则约束与自动化代码审查）**

这一层主要通过规则和专门的检查工具，进一步约束 Agent 的行为和代码质量。

例如：

- Rules：项目级编码规则和约束说明。
- AGENTS.md：告诉 Agent 如何理解项目、遵循哪些开发约定。
- Bug Bots：自动检查代码中的潜在 Bug、重复实现、冗余逻辑和常见反模式。
- Style Guide：统一团队的代码风格和实现约定，例如 Airbnb 或 Google 的编码规范。

这些机制能够弥补静态分析工具难以覆盖的部分。

例如，Linter 可以检查代码是否符合某些语法和格式规则，但未必能够判断某段逻辑是否存在不必要的重复，或者某种实现是否违背了项目的设计约定。这时候，Rules 和 Bug Bots 就可以提供额外的帮助。

不过，它们的可靠程度有所不同。

Rules 和 AGENTS.md 本质上仍然是自然语言指令，Agent 需要理解并主动遵循，因此无法保证每次都能正确执行。

而 Bug Bots 如果能够通过确定性的规则、静态分析或测试实现检查，就可以提供更稳定的保障；如果依赖 LLM 进行判断，则仍然需要考虑模型误判的问题。

因此，我们应该尽量将能够自动化的规则转化为工具检查，而不是仅仅停留在文本约定上。

**第四层：Skills（可复用的专业工作流程）**

Skills 可以看作对 Agent 能力的封装、扩展和约束。

它不仅可以告诉 Agent 某类任务应该如何完成，还可以为 Agent 提供相应的工具使用方法、操作流程和验证标准。

例如：

- Code Review Skill：按照团队约定的审查标准检查代码。
- Testing Skill：根据项目测试规范生成测试用例并执行验证。
- Refactoring Skill：按照既定的重构流程分析依赖、修改代码并检查回归风险。
- Performance Analysis Skill：使用 Chrome DevTools Protocol、Heap Snapshot 等工具分析性能问题。

Skills 的价值在于将原本需要人类反复指导 Agent 的经验沉淀下来，让 Agent 在遇到类似任务时能够复用。

例如，代码审查不应该每次都由开发者重新告诉 Agent 应该关注哪些问题。我们完全可以将团队的 Review 经验整理成 Code Review Skill，让 Agent 按照统一的流程检查代码。

同时，Skill 也可以集成 CLI、MCP 等工具，让 Agent 在需要时调用相应的能力，而不必每次都重新探索工具的使用方式。

需要注意的是，Skill 并不是强制执行机制。它更多是对 Agent 工作流程的引导和能力扩展，最终仍然需要结合测试、静态分析和人工审查来保证结果的可靠性。

**第五层：Style Guide & Human Review（风格指南与人工审查）**

这一层更多依赖团队经验和人为判断。

Style Guide 可以帮助 Agent 理解团队的编码习惯、设计偏好和一些难以通过工具表达的约定。例如，组件应该如何组织、函数应该保持多大粒度、什么时候应该抽象公共逻辑等。

而 Human Review 则负责处理那些难以完全自动化的判断，例如：

- 当前架构设计是否合理？
- 是否引入了不必要的复杂度？
- 是否存在潜在的业务风险？
- 这个实现是否符合产品的长期发展方向？

人工 Review 依然重要，但它也是最难规模化的一层。

当 Agent 每天可以生成大量 PR 时，如果每一份代码都需要人类逐行检查，那么人类最终会成为整个开发流程的瓶颈。

因此，我们更应该把有限的精力投入到更高杠杆的地方：改善架构、完善自动化检查、建立可靠的验证体系。

让人类从重复检查代码的工作中解放出来，更多地关注设计决策、系统质量和最终交付结果。

这里有一个值得记住的原则：

**越靠近代码和工具的约束，执行结果越确定；越依赖自然语言和人工判断，执行结果就越难保证。**

这并不意味着 Rules、Skills 或人工审查不重要，而是我们应该优先把能够自动化、能够强制执行的约束放到更底层，再利用自然语言规则、专业工作流程和人工经验补充那些工具暂时无法覆盖的部分。

## 二、Codebase as Memory：代码库就是 Agent 的记忆

这是视频中另一个让我印象深刻的观点：

**Your Codebase Is Memory。**

我们经常会讨论如何通过 Context Engineering 给 Agent 提供更多上下文，例如：

- 项目文档。
- AGENTS.md。
- Rules 和 Skills。
- 历史对话和任务记录。

但有一个容易被忽略的事实：代码库本身就是 Agent 最重要的上下文之一。

为什么？

因为 Agent 在开发过程中，往往会优先参考项目中已经存在的实现方式。

如果代码库中已经有一个类似的功能，Agent 很可能直接参考它的结构和写法，然后在此基础上进行扩展。

这意味着，代码库中的好模式会被继承，坏模式也同样会被继承。

如果我们没有及时处理技术债，那么 Agent 就可能不断复制已有的问题，让原本局部存在的 Anti-pattern 逐渐扩散。

因此，@poteto 提出了一个很有意思的角色定位：

**You are the gardener（你是代码库的园丁）。**

作为代码库的维护者，我们需要不断整理代码库，为 Agent 创造一个更容易走正确道路的环境。

具体来说，可以从三个方面入手。

### 2.1 清理技术债，避免 Anti-pattern 扩散

当我们发现代码库中存在不合理的实现时，不能只是想着以后有时间再重构。

因为 Agent 很可能会继续沿用这些实现方式。

例如：

- 多处重复实现相同的工具函数。
- 不一致的错误处理方式。
- 不合理的模块依赖关系。
- 过时的 API 和数据结构。
- 为了绕过问题而添加的大量特殊处理。

这些问题可能不会立刻导致功能故障，但会逐渐影响 Agent 后续生成代码的质量。

尤其需要注意的是，一些注释可能会成为 Agent 走捷径的依据。

例如，代码中存在一段不合理的逻辑，注释却写着「暂时不要修改这里」或者「这里有特殊情况」。

Agent 可能会直接继承这种处理方式，而不是进一步理解问题并尝试解决它。

当然，这并不意味着应该禁止注释。注释对于解释业务背景、设计原因和复杂约束依然非常重要。

真正需要避免的是：**用注释记录一个本应该通过架构、类型或者测试解决的问题，然后让这个问题长期存在。**

### 2.2 明确正确的 Pattern

除了清理坏模式，我们还需要明确项目中应该遵循的正确模式。

例如：

- 统一 API 请求和错误处理方式。
- 统一状态管理方案。
- 明确组件的组织和复用原则。
- 统一日志和监控方式。
- 明确模块之间的依赖关系。

当 Agent 需要开发新功能时，它可以直接参考已有的正确实现，而不需要每次都重新决定应该采用什么方案。

这相当于我们提前为 Agent 铺好了一条路。

**与其不断告诉 Agent 不应该怎么做，不如让它自然地知道应该怎么做。**

### 2.3 用 Lint 等工具对抗反模式

现实中，很多项目并不可能一次性解决所有技术债。

有些历史代码非常复杂，直接重构可能带来很大的风险。

这时候，我们可以先建立一些规则，明确哪些实现方式应该避免，哪些模式应该优先使用。

例如：

- 禁止新增某些已经废弃的 API。
- 禁止重复定义已有的工具函数。
- 限制不合理的依赖关系。
- 禁止随意绕过类型检查。
- 对某些反模式增加专门的 Lint 规则。

即使暂时无法清理历史问题，也应该尽量避免新的问题继续产生。

这可以理解为 Stop Bleeding（止血）。

从这个角度看，维护代码库不仅是在为人类开发者提供良好的工程环境，也是在持续优化 Agent 的工作环境。

## 三、Automation：建立自己的 AI 开发流水线

当我们已经具备了比较可靠的 Agent、验证体系和代码库之后，就可以进一步思考如何通过自动化扩大生产力。

这里有一个很有意思的比喻：

**Build your own Michelin Kitchen（建立自己的米其林厨房）。**

我们不应该让每一个 Agent 都从零开始理解整个项目、决定使用什么工具、探索如何运行应用。

相反，我们应该提前准备好一套面向 Agent 的开发 Framework。

### 3.1 为 Agent 构建专属 Framework

这个 Framework 的核心思想是 Minimal Context（最小上下文）。

Agent 只需要获得完成当前任务所必需的信息，其他事情交给预先构建好的 Framework。

例如：

- 如何启动应用？
- 如何运行测试？
- 如何操作浏览器？
- 如何收集日志？
- 如何验证功能？
- 如何检查代码规范？
- 如何提交 PR？

这些都可以提前封装成工具、CLI、Skills 和自动化流程。

这样一来，Agent 不需要每次都花费大量 Token 去探索项目环境，而是可以直接使用现成的基础设施完成工作。

这不仅能够减少上下文消耗，也能提高整个开发流程的一致性。

### 3.2 使用自己的 AI Infra

在基础设施完善之后，还可以进一步搭建自己的 AI Infra。

例如：

- 使用 Cloud Agent 提供独立的开发环境。
- 使用 Git Worktree 隔离不同 Agent 的工作目录。
- 使用 Coordinator 负责任务拆分、分发和结果汇总。
- 使用 Automations 根据事件自动触发 Agent。
- 使用 CI 和 Verification Skill 检查最终交付结果。

这样就可以逐渐形成一套自动化的开发流水线：

1. 收集 Bug Report、用户反馈或者开发需求。
2. 自动创建任务并分配给 Agent。
3. Agent 在独立环境中分析问题、修改代码。
4. Agent 运行测试并通过 Verification Skill 收集证据。
5. 自动创建 PR，并提供修改说明和验证结果。
6. 通过自动化检查和必要的人工审查完成交付。

随着验证体系越来越成熟，我们就可以逐渐减少人工介入，让 Agent 承担更多执行工作。

当然，这并不意味着应该一开始就启动大量 Agent。

更合理的顺序是：先让一个 Agent 能够可靠地完成任务，再考虑并行执行；先建立验证能力，再逐渐扩大自动化程度。

**Automation 的前提不是拥有更多 Agent，而是能够信任 Agent 的交付结果。**

## 四、总结：AI Coding 的核心是构建可信赖的工程体系

回顾整个视频，我认为 @poteto 分享的实践可以归纳为三个层次：

| 核心主题 | 解决的问题 | 关键实践 |
| --- | --- | --- |
| Trust | 如何相信 Agent 写出的代码？ | Verification Skill、CLI、Feature Map、静态分析 |
| Codebase as Memory | 如何让 Agent 更容易写出正确的代码？ | 清理技术债、统一 Pattern、完善架构和 Lint |
| Automation | 如何扩大 Agent 的生产力？ | AI Framework、Cloud Agent、Worktree、Coordinator、Automations |

这三个部分并不是相互独立的，而是逐层递进的关系。

首先，我们需要让 Agent 能够证明自己的工作是正确的。

然后，通过持续改善代码库，让 Agent 更容易理解项目，并减少重复犯错。

最后，当 Agent 的工作结果足够可靠时，再通过自动化和并行执行扩大生产力。

我觉得这里最值得借鉴的，并不是某个具体的 Skill 或者工具，而是一种工程思维的转变：

**不要把大量精力花在反复告诉 AI 应该怎么做，而应该把精力花在构建一个让 AI 更容易做对事情的环境。**

过去，我们需要通过 Code Review、技术文档和开发规范来约束开发者。

现在，面对 Agent，我们依然需要这些东西，但更应该思考：哪些约束可以通过架构实现？哪些规则可以通过工具强制执行？哪些经验可以沉淀成 Skill？哪些工作可以交给自动化？

当这些问题逐渐得到解决，AI Coding 才真正有机会从「AI 辅助编程」走向「Agent 驱动的软件工程」。

这或许才是所谓 PR Machine 背后真正值得关注的东西。
